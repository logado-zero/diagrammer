The Core Server Path

Eight techniques that let one Python process serve many people at once. Each is one paragraph in HOWTHEYWORK.md. This page opens each one up: the rule, the machinery underneath it, a picture, and the specific failure you get when it's missing.

They are not a checklist to work through in order — they are a set. Two are about shape, four about concurrency, two about what happens when something breaks. Every code claim below was read out of the repo, not inherited from the doc.

Where this page disagrees with HOWTHEYWORK.md

Checking each claim against the code turned up four that have drifted. Not every route is async def; the encoder is not the only CPU-bound work on the loop; only the subagent traces are centralised in run_agent(); and per-process state is a slightly longer list than "two lazy clients". Each is corrected in place below, marked like this box. The source doc is a summary written when those things were true — this is what the code says today.

Shape

Two techniques · where code is allowed to live

Both are about the same question: when three interchangeable providers all need the same behaviour, where does that behaviour go? The answer is not always "one place".

One choke point per cross-cutting concern

Every provider's output passes through run_agent(), so work that applies to all of them is written once there instead of three times.

The mechanism

run_agent() is an async generator that wraps whichever provider generator ran. Because every event has to pass through its async for loop on the way out, it can read, replace or inject events without any provider knowing. Its order is deliberate:

  • Retrieve memory first — before attachment inlining, so the retrieval query is the user's question and not the first rows of a spreadsheet.
  • Inline file attachments — by the time a provider runs, a .xlsx is already plain text.
  • Append recalled evidence last — to the final user message, behind everything stable, because evidence changes every turn and would otherwise invalidate a cached prompt prefix.
  • Dispatch to exactly one provider, then intercept diagram/chart events on the way out and run the subagent pass, bracketed by synthesized trace events.
  • Also here, and easy to miss: _clean_title() strips control characters from every payload title, and _node_colors() lifts per-node colours off the intent — both applied at the one point every provider's payload already passes through.

server/agent.py:127–200 — truncate → select_context → inline_file_attachment → capture last_user_text → append evidence → find_model_option → dispatch → intercept

Precision worth having — only some traces are centralised

The doc says trace events live in run_agent() "rather than three times over". Only the subagent traces do (six of them, plus "Recalling from memory…"). The web-search, web-fetch and memory-search traces are emitted inside each provider — what is shared is the label strings, in providers/dispatch.py. That matters because ProcessTrace.tsx renders them verbatim: centralise the strings and drift is impossible; centralise the emission and you would have to reach into three streaming loops.

What breaks without it

Attachment inlining, the subagent pass and every trace event get written three times, and drift the moment one provider is edited alone. The counter-rule matters just as much: when a feature needs genuinely different handling per provider — web search's tool definitions — that is the signal it does not belong in the choke point.

A choke point works on outputs, not on tool results

run_agent() can intercept a drawing tool because nothing flows back to the model. A tool whose result the model reads has to be answered inside each provider's own loop.

The mechanism

The distinction is terminal vs non-terminal. render_diagram and render_chart are terminal: the payload goes to the browser and the model is answered with a fixed string, "Rendered to the user." — nothing it says next depends on that reply. search_memory is the opposite: its result is the point, and it has to be fed back into the same tool-use loop the model is waiting on.

So the choke point centralises the input instead of the handling: it forwards one Scope and never touches the tool.

What can still be shared is the table underneath — tool name → client event → result string, plus the trace labels. That lives in providers/dispatch.py, and api.py and openai_provider.py each call it in one line. What stays per-provider is narrower than the doc's "three-line branch" suggests: it is the envelope around the result (tool_result with a tool_use_id vs function_call_output with a call_id) and when in the loop the result is produced, because a non-terminal result has to flow into the next request.

agent_sdk.py is the real exception, and takes only the constants: its MCP handlers are invoked by the SDK out of band and cannot yield, so it observes tool-use blocks and closes over the Scope per request instead.

server/providers/dispatch.py — dispatch_tool_call(name, payload, scope, events) → result string

Why the events come back in a list

dispatch_tool_call() appends client events to a list rather than yielding them, because its callers are already inside their own async def … yield … loops and need the result string in the same pass. It is the same out-parameter shape search_memory itself uses for its retrieval records — a function that must both emit side-effects and return a value, without being a generator.

What breaks without it

You try to centralise search_memory at the choke point, discover the tool result has nowhere to go, and reach for a per-request global to smuggle the owner id into a module-level handler. In agent_sdk.py a ContextVar looks like it works — until a handler runs on a different task than the one that set it, and then it fails by searching the wrong person's memory rather than by raising.

Concurrency

Four techniques · keeping one event loop free

All four defend the same resource: the single event loop thread that every concurrent user shares. Anything that holds it — a CPU burn, a slow constructor, a forgotten task — is felt by everyone at once.

async def end to end, and what's allowed to block

Every route runs on one event loop. Anything slow must be awaitable I/O, not CPU.

The mechanism

An event loop runs one piece of Python at a time. Concurrency comes from tasks yielding at every await — while one request waits on the network, the loop runs another. The model only holds while nothing occupies the thread without awaiting. Network calls (Anthropic, OpenAI, MongoDB via the async driver) and subprocess I/O already yield. A tight CPU loop does not: it holds the thread until it finishes, and every other request simply stops.

Two corrections this page owes you

"Every route is async def" is not true today. GET /api/health and GET /api/models are plain def (routes/meta.py). FastAPI notices and runs them in its own threadpool, so nothing blocks — but the mechanism is different from the rest of the app, and the claim is also asserted, wrongly, in main.py's own module docstring. Both are pure config reads with no I/O, so this is harmless; it is worth knowing precisely because it looks like a rule and isn't.

Where CPU still runs on the loop

The stronger claim — that the memory encoder is the only genuinely CPU-bound thing here — does not survive a grep. Three others run on the loop today, none of them offloaded:

None of these is a bug — scrypt is supposed to be slow, and the others are bounded. But ~100ms on the loop means a burst of logins is felt by everyone mid-conversation, and the honest version of this technique is "know which CPU work is on your loop and how long it holds", not "there is only one and it's handled". The encoder got the to_thread treatment because it was the one measured to matter; the others are candidates, not exemptions.

What breaks without it

Latency that scales with other people's traffic and never shows up in single-user testing. One synchronous embedding call would add its full duration to every request in flight, and the symptom — "the app is slow when several of us use it" — points at the wrong place.

CPU-bound work goes through to_thread, behind a semaphore

The memory encoder is the one genuinely CPU-bound thing here. It runs in a worker thread, and no more than four run at once.

The mechanism

Two separate guards, doing two different jobs, and it is easy to think one is enough.

  • asyncio.to_thread gets the work off the loop. This only helps because onnxruntime is native code that releases the GIL during inference — so the loop thread really does keep running Python while the forward pass proceeds. Wrap a pure-Python CPU loop the same way and you gain almost nothing: it would hold the GIL and starve the loop anyway.
  • The semaphore bounds how many run at once. to_thread submits to the loop's default ThreadPoolExecutor, which since Python 3.8 is sized min(32, os.cpu_count() + 4) — deliberately generous, because it is meant for I/O and for GIL-releasing native work. Left unbounded, a burst of concurrent turns would each take a thread and run a forward pass, and the CPU would be oversubscribed by whatever that number happens to be on the host. MEMORY_ENCODER_CONCURRENCY caps it at 4.
  • onnxruntime is capped a third time, inside the session. intra_op_num_threads = 2, inter_op_num_threads = 1. Unset, ONNX Runtime sizes its own intra-op pool to the physical cores — so --workers 4 would give four processes each a full-machine thread pool, all fighting for the same cores. The runtime's own docs treat setting this explicitly as the master switch for multi-process serving.

server/memory/encoder.py — _CONCURRENCY (MEMORY_ENCODER_CONCURRENCY, default 4); intra_op_num_threads = 2; inter_op_num_threads = 1

The one-time load sits outside the bound

encode() awaits _load() before taking the semaphore, so only the forward pass is counted against the limit of four. The ~4s first load is bounded by the lock instead — it can only happen once — but it can overlap with up to four in-flight encodes. That is why the warm-up at startup matters: it moves that 4s to a moment when nobody is waiting, rather than onto the first user's turn, where it would blow the 5s retrieval timeout and answer with no memory at all.

What breaks without it

Without to_thread: every concurrent request freezes for the length of a forward pass. Without the semaphore: a traffic burst runs as many passes as the executor has threads, and every one of them gets slower. Without intra_op_num_threads: single-process performance looks fine and --workers 4 is inexplicably slower than --workers 1.

Expensive clients are built lazily, under a lock

Check, take the lock, check again. Two concurrent first-requests must not build two.

The mechanism

Two places do this: openai_provider._get_client() and encoder._load(). The reason to be lazy differs — the OpenAI SDK throws in its constructor when no API key is set and the module is imported unconditionally, so a module-level client would crash startup for anyone using only Claude; the encoder's weights cost hundreds of MB of RSS and may need downloading first.

The second check is the part that looks redundant and is not. Between the first check and acquiring the lock there is an await — and every await is a point where the loop can run another task. Two requests can both pass the first check, then queue on the lock; without the re-check inside, the second one builds a client the first already built. Note this is not the classic Java double-checked-locking problem: there are no memory barriers or partially-constructed objects here, because a single-threaded event loop only switches at explicit suspension points. It is the same shape guarding a different hazard.

server/providers/openai_provider.py — _get_client(); server/memory/encoder.py — _load()

The exception worth knowing

providers/api.py builds its Anthropic client eagerly, at import time. That is not an inconsistency: Anthropic's SDK, unlike OpenAI's, does not throw when no key is configured — it only fails on the first request. Nothing is gained by deferring it.

What breaks without it

Without laziness: the server cannot start at all when OPENAI_API_KEY is unset, even for a user who only ever picks Claude. Without the re-check: duplicated clients and, for the encoder, hundreds of extra MB of resident memory that nothing ever frees.

Work that outlives the response needs a strong reference

asyncio keeps only a weak reference to a running task. Fire-and-forget without a reference can be garbage collected mid-flight.

The mechanism

Memory indexing embeds several units and may call a vision model. None of that belongs in front of a response the user is already reading, so it is scheduled and the request returns. The trap is that asyncio.create_task() returns a task the event loop itself does not keep alive — if nothing else references it, the garbage collector may take it while it is still running, and the work silently half-happens.

This is documented CPython behaviour, not folklore: the standard library docs tell you to save a reference, CPython tracked it as issue #91887, and Ruff ships a lint rule for it (RUF006 asyncio-dangling-task). The prescribed fix is exactly the shape this codebase uses — a module-level set, plus add_done_callback(set.discard) so finished tasks do not accumulate forever.

server/shared.py — spawn(); _background set; add_done_callback(_background.discard). Callers: memory ingest (routes/chat.py) and the encoder warm-up (main.py lifespan)

What breaks without it

Turns that are answered correctly, stored correctly, and then sometimes not indexed into memory — with no error anywhere. Weeks later, recall is quietly worse than it should be and nothing points at the cause.

Resilience

Two techniques · behaving well when something is missing

The first decides, per dependency, whether its absence is survivable. The second is what makes horizontal scaling free rather than a project.

Decide per dependency whether it degrades or fails

Enrichment degrades and says so quietly. The core fails loudly. The decision is made once per dependency, not per call site.

The mechanism

Every row below is a real try/except in the codebase, and the pattern is consistent: anything that improves an answer is allowed to be absent, and anything the answer is must surface. A turn that was answered and stored correctly must never be reported as broken because a background enrichment pass failed.

One detail in that last row is load-bearing: an errored turn writes no reply. That is exactly what a retry expects to find — the user's question stored, and no answer beside it.

What breaks without it

Decide this per call site instead of per dependency and you get both failure modes at once: a missing vision model that 500s a working chat turn, and a dead database that silently returns empty lists as though the user simply had no history.

Nothing is shared across requests, so --workers N stays free

No session state in process memory, no request-scoped globals. Scaling across cores is a command-line flag, not a refactor.

The mechanism

Sessions are rows in MongoDB, not entries in a dict; the Mongo client is a connection pool; a chat request carries its own full history. Grepping server/ for module-level mutable state turns up exactly four things, and none of them is request state:

  • encoder._session / _tokenizer — the loaded model, plus its _lock and _semaphore. A cache and two coordination primitives.
  • openai_provider._client / _client_lock — same shape.
  • api._client — the eagerly-built Anthropic client. Stateless per call.
  • shared._background — the strong-reference set from the previous technique. This one is genuinely written by every chat turn, and is the single place a leak could appear if a task never completed.
  • Plus the Mongo client, database and collection handles in db.py — a connection pool and a set of references, not state.

Every one is a cache or a coordinator whose absence would change latency, not correctness. That is the actual test for "shareable": if losing it would change an answer, it is state and it does not belong in the process.

Worth noting: HOWTHEYWORK.md says "the only per-process state is the two lazily-built clients". Grepping for `global` in server/ returns exactly two names — but the eager Anthropic client, the background-task set and the Mongo handles are module-level too. All harmless; the list is just longer than two.

What breaks without it

One in-memory session dict and --workers 4 logs users out at random, because request two lands on a process that never saw request one's login. It works perfectly in development, where there is only ever one worker.
