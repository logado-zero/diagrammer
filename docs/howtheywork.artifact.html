Architecture — server/*.py + src/

How Diagrammer Works

One request, one round trip. React sends the chat history — plus an optional image or text/sheet attachment — to a Python FastAPI backend, which asks an LLM — Claude or OpenAI, picked per request — the LLM streams text and optionally calls a render_diagram / render_chart tool (which one(s) it's even offered depends on the composer's draw-mode selector — see below), and the server relays every event straight to the browser over SSE as it happens. Only the last three messages are replayed into the prompt; anything older comes back through the memory layer, which is reached two ways — it retrieves automatically, before the model runs, on any turn that looks like it has a subject, and the model can also call search_memory itself. Either way it searches every conversation this user has ever had and hands back each hit tagged with its conversation title and turn number. Two more things happen around the answer: the turn is written to MongoDB as it streams, so a signed-in user can reopen the conversation later with its charts intact, and once the stream closes it is indexed into that same memory layer. Every request is handled concurrently, so multiple users can chat at once without blocking each other. Once a conversation has a diagram or chart, the chat view splits into a canvas panel (the latest one, full size) and a narrowed conversation column — see "Split-pane canvas" below.

Techniques on the core server path

The patterns the hot path depends on. They're collected here because each one recurs across several files, and because getting any of them wrong shows up as a whole-app problem rather than a local bug.

One choke point per concern
agent.py's run_agent() is the single place every provider's output passes through, so attachment inlining, the subagent pass and trace events live there rather than three times over. The same instinct puts persistence and memory ingest in routes/chat.py (route concerns, not generation concerns) and the tool list in tools.py. When a feature needs different handling per provider — web search's tool definitions — that's the signal it doesn't belong in a choke point.
…but only on outputs
Worth knowing before adding a third tool. run_agent() can intercept a diagram/chart event because those are terminal — the provider yields the event and answers the model with a fixed string, so nothing flows back. A tool whose result the model actually reads (search_memory) has to be answered inside each provider's own loop and can't be centralized the same way. What the choke point centralizes instead is the input: it forwards one Scope, and each provider handles the tool in its own three-line branch.
async def end to end
Every route runs on one event loop, which is what lets one process serve many users. The rule: anything slow must be awaitable I/O, not CPU. Network calls (Claude, OpenAI, MongoDB) and subprocess I/O (the agent-sdk CLI) already are.
CPU work off the loop
The memory encoder is the only genuinely CPU-bound thing here, and running it inline would freeze every concurrent request for a whole forward pass. memory/encoder.py wraps each call in asyncio.to_thread — onnxruntime releases the GIL, so the loop keeps running — behind a semaphore so N concurrent chats can't spawn N inference threads. onnxruntime's own intra_op_num_threads is pinned to 2 for the same reason: at its default, --workers 4 would have four processes each sizing a thread pool to every core.
Lazy clients, under a lock
Two places do this: openai_provider._get_client() (the OpenAI SDK throws in its constructor with no key, and the module is imported unconditionally) and memory/encoder._load() (weights cost hundreds of MB of RSS and may need downloading). Both use the double-checked pattern — check, take an asyncio.Lock, check again — so two concurrent first-requests can't build two.
Work that outlives the response
Memory indexing embeds several units and may call a vision model; none of that belongs in front of a response the user is already reading, so _spawn_memory_ingest schedules it and returns. The non-obvious part: asyncio holds only a weak reference to a running task, so a fire-and-forget create_task() nobody keeps can be garbage collected mid-flight. _ingest_tasks is a module-level set each task discards itself from.
Nothing shared across requests
Sessions live in the database, not process memory; the Mongo client is a connection pool; the only per-process state is the two lazily-built clients above, and both are caches whose absence changes nothing but latency. That's why uvicorn server.main:app --workers 4 still needs no code changes.

Decide per dependency whether it degrades or fails. The pattern throughout is that enrichment degrades and the core fails loudly:

The memory layer

server/memory/ indexes what happened so it can be retrieved later, and gets it back in front of the model. It writes in a background task once the SSE stream has closed, so encoding and the image-description call never sit in front of a response. It reads through two entry points into one retrieval core: push — select_context() retrieves on every turn that looks like it has a subject, before any provider runs — and pull, the search_memory tool the model calls when it wants something specific.

Together they are what makes agent.py's HISTORY_LEN = 3 safe rather than lossy. The model gets the last three messages, and everything older — earlier turns, other conversations, and the full contents of attachments rather than the truncated copy inlined into the prompt — is either already attached to the turn or one tool call away.

Why both, when the tool already existed. Pull alone has a hole, and it isn't the model being lazy: to decide it should search, the model has to first notice something is missing — and the whole problem with a truncated history is that what was truncated leaves no trace in what remains. A question that needed the warehouse study from three weeks ago looks, from inside a three-message window, exactly like a question that didn't. So retrieval also runs unprompted. Both paths call the same search(), format with the same format_hits(), and write the same retrieval_record(); the only difference recorded anywhere is a source field of "auto" or "tool".

What gets kept

  • The guiding rule is the opposite of most memory systems: store the original, never a summary. A chart payload already holds its exact title, series names and numbers — paraphrasing throws away the thing a follow-up needs.
  • So a chart unit keeps the raw payload verbatim, and the text that gets embedded is only a retrieval handle.
  • Images are the deliberate exception: there's no text in an image, so a vision model writes a description at ingest and that is what gets embedded. It's the one generative call in the whole memory path, it happens after the response is sent, and if it fails the image is still stored — just not searchable by content.
three views, fused

How retrieval works

  • Dense (Harrier embeddings) catches paraphrase and cross-language matches; lexical (Mongo $text) catches exact names, dates and numbers; graph catches units that share no words and no meaning with the query but sit two hops from it through an entity.
  • Each view's scores are min-max normalized independently, then weighted and summed — a $text score, a cosine similarity and a PageRank mass aren't remotely on the same scale, so adding them raw would let whichever view produces bigger numbers decide the ranking.
  • A unit several views agree on outranks one only a single view found. That's the behaviour that makes this better than any one of them.
  • Measured: an English query retrieves a Vietnamese document with the lexical view contributing exactly 0 — the payoff of a multilingual encoder, and why bge-small-en was ruled out. Measured again on real data: a sheet unit ranked second on graph: 1.0 where lexical gave it 0.025.

The gate, and the two strings. Auto-retrieval costs an encode plus a vector scan (~145 ms) in front of a waiting user, and "hi" has nothing to retrieve for — so profile.py skips greetings, acknowledgements and anything too short to carry a subject, at ~0.1 ms. The part that is easy to get backwards: the gate reads only the message just sent, because profiling the pair would make a "hi" following a long assistant reply look substantial and the gate would never fire — while the query is the last two messages, because querying on one loses the subject of every bare follow-up. "Change the colour to blue" is a sentence whose object is in the turn before it.
The graph view, concretely. entities.py extracts what a unit is about — tickers, amounts, dates, quoted titles, plus ordinary content words to fill the budget — and memory_edges links any two seen together. At query time the same extractor runs over the query, a bounded two-hop neighbourhood is loaded, and Personalized PageRank spreads activation from the query's own entities across it; units are then scored by the activated entities they carry. No networkx — a textbook power iteration over a dict-of-dicts on a graph of hundreds of nodes.

There is no NER model, and that isn't a shortcut. en_core_web_sm is English-only and fails outright on the Vietnamese this app is used in, and a multilingual one is a dependency, a download and a forward pass per unit at ingest. What replaces it fits better than it sounds: the graph records observed co-occurrence, not inferred semantics, so precision matters far less than for a knowledge graph — and what these units actually contain is exactly the category regex handles best and NER handles worst.
Evidence closure. After fusion, the units immediately before and after the top few hits are pulled in even though they matched nothing — flagged is_context with a score of 0, and labelled as such in what the model reads. A hit is one message out of a conversation, and some messages have their subject in the one before them. They're appended after the real hits rather than ranked among them, so nothing about the ranking changes, and the model is told they didn't match: a model told these are results will cite them as answers.

The pull path: search_memory

The model calls it with one field, a query string. memory/tool.py runs the search and renders the hits as text — the only shape all three transports agree on, since an Anthropic tool_result, an OpenAI function_call_output and an MCP text block are three envelopes around the same string. Each hit is labelled before its content:

The label is the point. A model handed bare text has no way to say where it learned something, so it either omits the source or invents one; handed a conversation title and a turn number it writes "in 'Q3 review', turn 14" and the user can go check. That is verbatim what the live run produced — "4,820 pallets, across three bays — from 'Warehouse capacity study', turn 1" — asked in a conversation that had never mentioned the warehouse.

kind is there so a partial source announces itself: a sheet hit is one window of a bigger file, and the model should know neighbouring rows exist. For chart and diagram hits the raw payload rides along as compact JSON, since the exact numbers are the whole reason extract.py keeps it verbatim next to the prose.

Two rules the formatter follows, both because the consumer is a model rather than a screen. Never return an empty string — a blank tool result reads as a malfunction, and the usual reaction is to call the tool again with reworded queries, so "no matches" is spelled out as a sentence that closes the subject. And budget the output: a sheet window is a hundred-row markdown table, and ten returned verbatim would cost more context than the truncated history the tool exists to compensate for. How many come back is MEMORY_SEARCH_LIMIT, default 10, read per call and clamped.
What came back is logged, not displayed. retrieval_record() builds one entry per search — the query, a status, a source, and a list_result array holding each hit's rank, conversation, ids, seq/role/kind, score, viewScores and a capped text preview. Both entry points yield it as a retrieval event and routes/chat.py files it into agent_logs.steps, then continues before the SSE yield: it is the one event the browser never sees. The chat UI gets a "Recalling from memory…" or "Searching memory…" status line and nothing else.

source is worth more than it looks. A turn that retrieved automatically and then had the model search anyway means either the automatic query was wrong or the model didn't notice what it was handed — and neither is visible without a field that tells the two apart.
Two details before touching that record. viewScores is the field that earns the structure — it says why a hit ranked where it did, and a view missing from the dict returned nothing at all for that query. And ids are stringified at construction, because GET /api/conversations/{id}/logs hands steps straight to FastAPI's encoder, which handles datetime but raises on ObjectId; a raw id would break only that route, and only once someone actually read a log — so a recursive no-ObjectId walk is one of the self-check's assertions. run_search_memory() takes the list as a sink rather than returning it, because agent_sdk.py's MCP handler can't yield at all — it only shares a closure with its provider loop, which drains the list as messages arrive.
It first shipped as one trace event per hit, and that was wrong twice. Reusing an existing pipe was the smaller diff and it cost the thing itself: it put raw retrieval internals in the chat UI where a user reads their answer, and — because a trace step is just {type, label, at} — it flattened the log too, turning one search into seven sibling rows with the interesting part crammed into a truncated string. Match the event shape to the thing, not to the transport that's already there: a search is one event that contains a list. Splitting "show the user what happened" from "record what happened" is what let the record get richer and the UI get quieter at the same time.
A retrieval tool isn't shaped like this app's other tools. render_diagram/render_chart are terminal — the provider yields an event and answers the model with "Rendered to the user.". search_memory feeds real content back into the loop and needs per-request identity, and that one difference drove the whole design: it can't be intercepted at agent.py's choke point, so agent.py forwards a Scope and each provider answers the tool in its own loop. In agent_sdk.py the MCP server is now built per request, because an MCP handler receives only the tool's arguments — there is no context parameter — so the only way to give it an owner is a closure. A ContextVar would have worked until a handler ran on a different task than the one that set it, and would have failed by searching the wrong person's memory rather than by raising.
The scope is the entire security boundary. search_memory's schema has exactly one field. There is no owner or conversation parameter, so the model cannot widen what it sees and a prompt injection inside a retrieved document has nothing to aim at. The Scope comes from the session cookie via routes/chat.py's _memory_scope(), which returns None when MEMORY_ENABLED=0 — and None removes the tool and its prompt text, leaving a request byte-identical to what the app sent before any of this existed.
A truncation limit belongs to its consumer. attachments.py's MAX_ROWS = 300 is a prompt budget — it stops an attachment crowding out the conversation — and it has no business binding what gets remembered. sheet_row_windows() chunks the whole sheet into overlapping windows, each repeating the header so a chunk read alone still has column names. A live test made the point better than the reasoning did: on a 420-row sheet the assistant answered "300 regions" from the truncated prompt while memory held all 420.
Tenant isolation is structural, not remembered. Every function in store.py takes a Scope first, Scope can't be constructed without an owner id, and nothing accepts a raw Mongo filter. Dense scoring filters before loading vectors rather than after ranking. This is the highest-severity bug class in a retrieval system: a missing owner filter raises nothing, logs nothing, passes every test written with one user, and puts someone else's private conversation into a prompt.
The graph made that harder, not easier. Every other query filters ownerId once, at the leaf. A walk hops entity → unit → entity — and entity strings are inherently global: "warehouse" is a legitimate node in every account's graph, so nothing about the string distinguishes one person's subgraph from another's. The structural answer is that load_adjacency() pulls the whole neighbourhood up front through one owner-filtered function and the walk then runs over that dict — it never queries mid-traversal, so it cannot leave the tenant however many hops it takes.

python -m server.memory.demo is the merge gate. It seeds two users with near-identical text and a deliberately shared entity, gives each a private entity nobody else has, and asserts from both directions that the private one is never reachable — through neighbours(), the PPR walk, units_by_entities(), evidence closure, select_context()'s prompt output, or the agent_logs record. Assertions compare ids and titles, never text, because the seeded users say the same thing on purpose.
Embedding provenance is recorded on every unit. embedModel, embedDim and embedSpace are written but nothing reads them yet. A vector only means anything relative to the model that produced it: swap encoders without recording which one ran and every stored vector silently becomes noise against new queries — no error, just worse results nobody attributes to the change. store.dense() filters on them, so mixing spaces is impossible rather than merely discouraged.
Stated ceiling. Dense scoring is a brute-force dot product over one owner's vectors in this process — MongoDB Community has no $vectorSearch. Because every query is owner-scoped, cost tracks one user's history depth, not the user count. Roughly fine to ~10k units per user (~25MB of float32 at 640 dims); past that, a real vector index goes behind the same store.dense() signature.

A warm search costs ~145 ms — one query encode plus the scan — and unlike ingest it is on the response path, now on every turn that clears the gate rather than only when the model chose to search. The cold number is the one that bites: the encoder loads lazily and that first load is ~4 s, which would land on the first turn after every boot and --reload, reliably enough to trip the retrieval timeout and answer that turn with no memory at all. main.py's lifespan schedules a warm-up at startup so nobody's first question pays for it.

Edges are pairwise, so their write cost is quadratic in entities per unit. Hence the caps: 24 entities stored per unit, top 12 linked, top 6 for cross-unit adjacency, and sheet units extracting from their header only — one uncapped 100-row spreadsheet window is tens of thousands of edges.
What is still a seam rather than a feature. The fusion function takes a list of named views rather than hardcoded arguments, so a fourth is one more entry. And query-dependent weights are already a parameter (search(…, weights=…)) that nothing computes — it defaults to a fixed dense 0.5 / lexical 0.3 / graph 0.2 that nothing has measured either. The instrument for fixing that already runs: viewScores on every hit of every logged retrieval says what each view actually contributed.
There is no relevance floor, and that is deliberate. Cosine similarity always has a nearest neighbour, so an unrelated query still returns this owner's top-ranked units rather than nothing — found by writing an assertion that expected "no matches" for a nonsense query and getting the corpus's only document back instead. No threshold is applied, because picking one without an evaluation set is guessing. The mitigation is in the prompt: the model is told results always come back filled, and to judge each one rather than stretch it to fit. The self-check pins the behaviour so nobody rediscovers it as a bug.

The subagent pass

agent.py's run_agent() sits between every provider and the SSE relay, so it's the one place that can intercept a diagram / chart event regardless of which of the three providers produced it. When it sees one, it awaits a second, specialized, forced-tool-call LLM turn (server/subagents.py) before forwarding the event on.

run_flowchart_subagent

Flowchart Agent

  • The render_diagram tool call is unchanged (still nodes/edges/kind/direction) — the subagent's output format is what changed, to a new emit_mermaid_flowchart tool ({title, mermaid}).
  • Job is judgment, not geometry: pick each node's kind, tighten labels, fill in missing decision-branch edge labels.
  • Decides handDrawn vs classic look per request — reads the user's own latest message for it.
  • Positions are Mermaid's own problem now (its built-in layout engine) — the subagent never sees or sets coordinates.
run_chart_subagent

Data Chart Agent

  • Not just bar/line/pie — picks whichever ECharts form fits the data: scatter, radar, funnel, gauge, heatmap, candlestick, sunburst, waterfall/stacked bar, and more.
  • Caps categorical cardinality at 8 (bars, pie/donut/rose slices, radar items) — past that, folds the smallest into "Other" rather than generating a 9th hue.
  • Bakes in mark specs for legibility: bar radius/max-width, line width, marker size, area-fill opacity, sparing direct labels.
  • Told never to set color — ChartCard.tsx picks which of palette.ts's ramps to layer on by the option's own structure: categorical (default), sequential (a visualMap or gauge series), or the fixed good/critical pair (a candlestick series).
  • Keeps theme switching instant and client-side instead of a third LLM round trip.
Graceful fallback. Both subagents degrade gracefully if no subagent LLM client is configured, or the call fails: the flowchart pass builds basic Mermaid syntax with a small deterministic Python mapping (_fallback_mermaid_flowchart), and the chart pass builds a basic ECharts option the same way (_fallback_chart_option) — so the app still works end-to-end with zero extra setup.
Why tools.py also changed. The primary model never sees the subagent's output, only its own render_chart tool definition — so when that description still said "bar, line, or pie," a Claude Opus run was caught live telling a user "no gauge type available" and drawing a pie instead, even though the subagent fully supports gauges. Fixed by widening RENDER_CHART_TOOL's description and SYSTEM_PROMPT in server/tools.py, and loosening chartType from a closed enum to a free-text hint — the one shared file every provider's primary tool call routes through.

ChartCard.tsx also carries two export actions in its header: Copy writes a PNG straight to the clipboard, and Download offers PNG or JPG — both via echarts-for-react's own getEchartsInstance().getDataURL() (no new dependency) plus the native Clipboard API, feature-detected so Copy hides itself where unsupported.

Flowchart rendering: Mermaid

DiagramCard.tsx calls mermaid.render() client-side on whatever the Flowchart Agent generated. Color follows the same principle as charts — the subagent never emits literal colors, the client applies the app's own validated palette — but the mechanism differs because Mermaid has no option.color-style hook: DiagramCard.tsx appends a fixed classDef header (five rules, one per node kind, built from palette.ts) to the end of the subagent's Mermaid body before rendering. Appending rather than prepending means it never has to reason about where an optional YAML frontmatter block (the handDrawn look, when the subagent decides the user asked for one) ends — frontmatter only has to be first, and a classDef works from anywhere in the flowchart body.

Per-node colors, when the user asked for them. The primary model can set a node's color in the render_diagram call — for "make the blocks match the colors in this image", say. agent.py's _node_colors() lifts those off the intent into a colors map on the payload, and buildColorOverrides() compiles each into a classDef ncolorN plus a class <id> ncolorN statement appended after the kind header. The node carries both classes and CSS source order decides, so the override wins; label ink is picked from the fill's relative luminance.

It deliberately does not travel as Mermaid style lines from the subagent. The same color needs a different declaration per look — hand-drawn must restate SKETCH_STROKE_WIDTH, classic must not — and the hand-drawn toggle is client state the server cannot see. Sending {id: color} and letting the client compile it keeps one color correct across all four combinations of look and theme.

No server-side validator exists. Checked directly: the real @mermaid-js/parser package only covers newer diagram types Mermaid has migrated to a proper grammar — pie, architecture, gitGraph, radar, treemap, etc. — not flowchart, which is still browser-only legacy grammar. Given that, DiagramCard.tsx wraps mermaid.render() in a try/catch with a clear fallback UI (error message + the raw source in a collapsed details block) rather than crashing the message list, and the subagent's prompt encodes the rules below as the closest available substitute for real validation.

Every one of these was found by actually breaking it live, not by guessing:

Semicolons
Anywhere in label/edge text, silently break the whole diagram — Mermaid's grammar treats ; as a statement terminator.
The word "end"
Is a reserved keyword (closes subgraph blocks) and breaks parsing as a class name or as a node's own id. Naming the class endNode fixed the first case; the node-id case slipped through later, because the prompt tells the subagent both to preserve the primary model's node ids exactly and to avoid end — which conflict whenever the primary model names its final node end. A prompt instruction that has already failed once needs a code backstop, not stronger wording: _rename_reserved_end() runs on every output, LLM and fallback alike.
HTML labels taint canvases
Mermaid's default <foreignObject>-based labels taint any <canvas> the rendered SVG is later drawn onto — breaking the Copy/Download actions with "Tainted canvases may not be exported." Fixed with mermaid.initialize({ htmlLabels: false }), forcing plain SVG <text> labels.
A quoted id in a class statement
class "weird id" ncolor0 is a parse error that takes the entire diagram down, while class anIdThatDoesntExist ncolor0 renders fine and is silently ignored (no ghost node) — both measured in a throwaway render before the color feature was designed around them. Node ids come from the model, so _node_colors() drops any id that isn't [A-Za-z][A-Za-z0-9_]*: a lost color beats a lost diagram. The same probe confirmed the other half of the design — a later class statement beats an earlier :::kind tag, in both looks.
Hand-drawn's solid fill
Mermaid hardcodes fillStyle: "hachure", so a node's "fill" is really parallel diagonal pen strokes — 4px wide on a 5.2px gap. A classDef compiles to CSS with !important on every <path>, overriding rough.js's own line width, so pushing SKETCH_STROKE_WIDTH past the gap makes adjacent strokes overlap into continuous color. It's 7px. Under ~5.2px the diagonal striping returns — recognize the symptom, it isn't a new bug. The same width thickens the outline, which is why each node kind uses one color for both fill and stroke.

Theming: light / dark / system

Two kinds of consumer need to know the theme and they can't share one mechanism. Tailwind's dark: utilities need a class on <html>; ECharts and Mermaid need a boolean in JS to pick a palette. src/lib/theme.ts owns both, from one stored value, so they can't disagree.

Behind useSyncExternalStore. The two components that consume the boolean are memo'd leaves at the bottom of the tree; passing the theme down as a prop would re-render them on every parent render, which is exactly what the memo exists to prevent. No context provider, no new dependency.

Attachments: Image / Text / Sheet

The composer's attach popover offers three kinds. image goes to provider-specific multimodal content blocks, handled independently in each provider's _to_*_messages() — on every user message that carries one, not just the last. toOutgoing() resends an image on each turn of its conversation and HISTORY_LEN keeps it in the window, but both converters used to attach it only at i == last_index, a condition written back when only the opening turn could have one. The symptom was a follow-up about an uploaded picture — "make the blocks match its colors" — answered by a model that had been handed nothing but that message's text. Trace the whole path before blaming the end of it: that looked like history truncation and was a one-line condition three layers down. One gap remains: after a page reload the client holds a display-only attachment reference and sends image: null, so the picture is gone until the GridFS blob is re-inlined server-side. Text and Sheet (.xlsx or .csv) are different: both just need to become plain text before any provider sees them, so they share one wire field, ChatRequestMessage.file ({name, mediaType, data}), and one choke point — server/attachments.py's inline_file_attachment(), called from agent.py before dispatching to any provider. It decodes the bytes to text for text/plain and text/csv (a .csv is already plain text, so it needs no special-casing at all), or parses the first sheet with openpyxl into a markdown table (capped at MAX_ROWS) for the xlsx mimetype specifically, and prepends the result to that message's text. No provider file needs to know file exists — by the time any of them run, it's already ordinary text. The client decides which mediaType to send based on the picked file's extension, not the kind alone.

_decode_text() sniffs the encoding rather than assuming UTF-8, and that's load-bearing, not defensive. Excel on Windows writes plain "CSV" in the system ANSI codepage — cp1258 on a Vietnamese locale, cp1252 on a Western one — and "Unicode Text" writes UTF-16; only "CSV UTF-8" writes UTF-8, and then with a BOM. So it checks for a UTF-16 BOM first (a bare decode("utf-16") with no BOM guesses little-endian and silently succeeds on ordinary Latin text, which is why that can't just be another rung), then tries utf-8-sig → cp1258 → cp1252 strictly, and only then falls back to lossy errors="replace". Every result is unicodedata.normalize("NFC", ...)d, because cp1258 can't encode a precomposed ỏ/ố at all — it stores base letter + combining tone mark, which renders correctly but won't string-compare or slugify.
This is the one place in the backend where text could be lost, and it was. Attaching a Vietnamese CSV used to turn every accented character into U+FFFD (TEU kh□ng h□ng) before the LLM ever saw it, so the chart faithfully rendered mojibake. Worth internalizing the tell: one box per accented character means the text was destroyed upstream; it is never a missing font, since à/á/ã exist in every font ever shipped. python -m server.attachments covers all four encodings.
Two copies, two budgets. The function above builds the prompt copy, capped at 300 rows. sheet_row_windows() in the same file builds the memory copy — the whole sheet in overlapping windows, uncapped — because a prompt budget has no reason to decide what stays answerable later. Both share one row-to-markdown helper so a sheet always renders the same way. See "The memory layer" above.

Split-pane canvas + cross-turn edits

ChatView.tsx computes the single latest diagram/chart across the whole conversation (findLatestVisual, newest message first). Before one exists, chat looks exactly like before this existed — one centered column. Once one exists, it splits: CanvasPanel.tsx renders that diagram/chart full-size on the left (DiagramCard/ChartCard, now sized by their flex parent instead of a fixed pixel height), and the message list + composer narrow into a column on the right. MessageBubble.tsx no longer renders diagram/chart cards inline — just a small "Updated the chart/diagram — see canvas" note.

How a follow-up actually revises the canvas. For the model to revise what's on canvas (not just draw something new next to it), it has to see what it drew last turn — but lib/api.ts's toOutgoing() only ever replayed text, stripping diagrams/charts out of history entirely. withVisualContext() fixes this: for an assistant message that produced a diagram/chart, it appends a compact JSON block ([Previously rendered chart: {...}]) to that message's replayed text. That's the whole mechanism — no "edit" tool, no special mode; the model just sees its own prior output as context, and the canvas naturally shows whatever the latest turn produced.

Process Trace

While a diagram/chart tool call is being polished by a subagent (previously a silent pause after the streamed text), agent.py now emits {"type": "trace", "label": str} events around that call: which subagent activated, its own forced tool call, then its result — three real phases, not fabricated progress steps. ProcessTrace.tsx renders them as a collapsible box in MessageBubble.tsx. It emits one more before the provider even starts — "Recalling from memory…" — when the push path retrieved something, and all three providers emit the same event type for web searches (below) and for search_memory, so a searching turn shows "Searching the web…" or "Searching memory…" through the same box. A turn where the gate skipped retrieval shows nothing: it is logged, but there was no work to watch, and inventing a step for it is exactly the fabricated progress this box exists without.

Status lines only. What a memory search actually returned does not come through here — that's a retrieval event, filed into agent_logs and never relayed (see "The memory layer"). This box is for what the turn is doing, not for retrieval internals.

It stays after the turn ends — the spinner becomes a check and the list collapses itself, with a manual click winning from then on. It used to render only while isStreaming && !text and vanish the instant the reply began; keeping it costs one collapsed row and answers "did this turn search anything?" after the fact. routes/chat.py persists reply["trace"], so the labels survive a reload too.

Agent flow in backend

One turn, step by step: POST /api/chat's event_stream() calls _begin_turn() (creates or loads the conversation, writes the user's message), then loops async for event in run_agent(...). run_agent() is the one cross-provider choke point: it inlines any file attachment, resolves the model catalog entry, and dispatches to exactly one of server/providers/{api,agent_sdk,openai_provider}.py, each streaming the same event shape. A diagram/chart event is intercepted there before it ever reaches routes/chat.py, run through the matching subagent, and rewrapped with the trace events described above. Back in event_stream(), each event is re-emitted to the browser as SSE and accumulated — text appends to the reply, trace appends to reply["trace"] — and on done the assistant message is written to conversations, a title may be generated, and memory ingest is scheduled.

Every provider (api.py/agent_sdk.py/openai_provider.py) yields the same AgentEvent shape into the same loop — agent.py only branches on the event type, never on which provider produced it. Persist is where the new agent_logs turn (see below) is written, alongside the existing assistant-message save.

Logging is not agent.py's job. agent.py has no per-request identity — it's shared by three providers and knows nothing about which conversation or user it's serving. conversation_id/ownerId only exist one level up, in event_stream(), which is why persisted step-logging hooks in there instead of at the choke point.

Persisted agent-step log. Beyond the Process Trace box, every turn's steps are also written to a durable agent_logs collection (server/db.py) — one document per turn: {ownerId, conversationId, startedAt, endedAt, status, steps}. event_stream() appends a step for each trace event (the same phases the UI shows) plus a terminal done/error step, then inserts the document once the turn ends — trace-level, not every raw provider event, so no text deltas and no tool_use blocks. Read it back via GET /api/conversations/{id}/logs, owner-scoped through the same _owned_conversation() check as the other conversation routes, newest turn first.
One step type goes further than the UI, in both directions. A retrieval step is richer than a label — {type, label, query, status, source, list_result, at}, where list_result holds one structured record per hit — and it is the only one the browser never receives, because event_stream() continues past the SSE yield for it. The log is a superset of the trace, not a copy of it: this is where you look to see what a memory search actually returned, which entry point ran it (source), and — via viewScores — which of the three views put each hit where it landed.
The push path needed no change here at all. When automatic retrieval landed, routes/chat.py already relayed trace and already filed retrieval without forwarding it — so agent.py emitting those two events before the provider starts was the entire wiring. That is what a choke point is worth: the event type built for one caller carried a second one for free.

Live web search

Ask "what's the gold price in Vietnam today?" and the model used to say it had no access to live market data and suggest you go look it up and paste the numbers back. Now it searches.

Nothing in this repo implements searching. There is no search API key, no HTTP client fetching result pages, no summarize step — it's a capability the provider already has, and the whole change was turning it on and telling the model when to use it. Each transport has its own, so unlike almost everything else here the tools are declared per provider rather than in the shared tools.py.

TransportToolsRuns where
api.py web_search_20260209, web_fetch_20260209 (SERVER_TOOLS) Anthropic's servers — results come back inside the same response, so there is no handler here and no tool_result to send
agent_sdk.py WebSearch, WebFetch (BUILTIN_TOOLS) The local claude CLI subprocess
openai_provider.py {"type": "web_search"} (SERVER_TOOLS) OpenAI's servers, via the Responses API

web_search is the Google-shaped one: a query in, ranked hits out, with titles, URLs and snippets. web_fetch (Claude only) opens a single page — one of those hits, or a site the user named. Search finds the page; fetch reads the numbers off it. A real turn uses both: on "chart the SJC gold sell price over the last 5 days" the trace box shows Searching the web… → Reading a page… → Searching the web… and then a chart appears with real dates on it.

Searching is not just for answering. The shared prompt (WEB_TOOLS_PROMPT) also covers drawing: if a chart needs data the model doesn't have, it searches for it rather than asking you to paste numbers in — and it's told to leave out anything it can't source instead of inventing it, and to say which points it had to approximate. That shows up verbatim in real replies: "4 Aug wasn't available, so I substituted 1 Aug to keep five sourced points."

Why the OpenAI provider is on the Responses API. This is the whole reason it isn't on Chat Completions. There, web search and function calling are mutually exclusive — measured, not assumed: gpt-4o rejects web_search_options outright, gpt-4o-search-preview (the model that does search) rejects tools, and gpt-5.6-luna calls the parameter unknown. Giving up tools would mean giving up render_diagram and render_chart, so the provider moved to /v1/responses, where the two coexist. This page briefly said "OpenAI genuinely can't search" — that was wrong, and testing one API surface then generalizing to the whole vendor is the mistake to avoid. The migration also deleted the old reasoning_effort: 'none' workaround, which existed only because Chat Completions refused function tools on reasoning models.

Two things in api.py had to change to survive server tools — both latent bugs, not new features:

_serialize_assistant_content
Enumerated the block types it knew about (text, tool_use) and dropped the rest. A turn that searched and drew would lose its server_tool_use / web_search_tool_result blocks when the tool loop replayed history — and the API rejects a result block whose tool-use block has gone missing. The fix deleted more code than it added: [b.model_dump(exclude_none=True) for b in blocks]. A serializer that enumerates the cases it knows about is a bug waiting for the next case.
stop_reason "pause_turn"
Means a server tool hit the API's own internal iteration limit and the turn stopped mid-search. It used to fall into the "not a tool call, we're done" branch and truncate the answer. Now it re-sends the conversation as-is; the trailing server_tool_use block is what tells the server to pick up where it left off.

Accounts and stored history

Everything here lives in one MongoDB database, chart-chatbot (server/db.py). Messages are embedded in the conversation document rather than kept in their own collection: one read reopens a whole conversation, and the stored diagrams/charts are the same final payloads the client already renders, so reopening a chat redraws its charts with no LLM call. memory_units is a separate collection, for the opposite reasons — it's written asynchronously after a turn, queried per-owner across conversations rather than per-conversation, and its vectors would bloat a document that's read in full on every reopen.

A message's attachment is {blobId, mediaType, kind: "image" | "file", name?} — a reference into this same GridFS bucket, uploaded by routes/chat.py's _stored_user_message() and turned into a fetchable GET /api/attachments/{blobId} URL when a conversation is reopened, so switching away and back never loses what was attached. userId is the handle a person types; ownerId is the ObjectId foreign key back to users._id. Two names on purpose — one string the user chose, one id the database chose. Every memory index leads with ownerId, which is what keeps one user's history depth — rather than the size of the user base — the thing that governs query cost.

server/auth.py

Sign-in

  • A user ID and password, hashed with stdlib hashlib.scrypt — no bcrypt, no passlib.
  • Login writes a sessions row and sets its random token as an httpOnly cookie; current_user() is the only place that cookie becomes a user.
  • Sessions are rows rather than JWTs specifically so signing out revokes access instead of waiting for a token to expire.
  • "Continue as guest" is not a separate unauthenticated mode — it creates an ordinary user row with a generated guest-xxxxxxxx id and an empty passwordHash that verify_password() can never match. Every route works unchanged; the account just can't be signed back into once the cookie is gone.
server/routes/chat.py

Saving a turn

  • Happens inside POST /api/chat's event_stream(), not in agent.py — run_agent()'s job is provider dispatch, and persistence has no business in it.
  • The user's message is written on entry; the assistant's reply is buffered as its events stream past and written once on done.
  • An errored turn writes no reply — which is exactly what a retry expects to find.
  • An attachment still isn't inlined into the conversation document — that would put megabytes of base64 under Mongo's 16MB ceiling. Its original bytes go to GridFS instead (the same bucket the memory layer uses); the message stores only a {blobId, mediaType, kind, name?} reference, turned into a GET /api/attachments/{blobId} URL on the way out — so an image/sheet is still there the next time the conversation is opened.
  • Deleting a conversation asks first. Sidebar.tsx's trash button opens a native <dialog> naming the conversation rather than calling the handler; only its Delete button reaches handleDeleteConversation. showModal() supplies the backdrop, Escape, focus trapping and top-layer stacking above the sidebar's own z-30, so nothing is hand-rolled — the one thing it doesn't supply is centering, because Tailwind's preflight zeroes the UA stylesheet's margin: auto. The confirm is purely a view concern; the cascade below is unchanged.
  • Deleting a conversation cascades to its memory units and their GridFS blobs, its own messages' attachment blobs (same bucket, deleted directly since these aren't memory units), and agent_logs. Without that, deleted content would stay retrievable — both a correctness and a privacy bug, since being gone is what the user asked for.
  • Graph edges are the one thing withdrawn rather than deleted. They're owner-scoped, not conversation-scoped, and the same entity pair may well have been observed in conversations the user is keeping — so the delete regenerates exactly the edges this conversation contributed (through the same function that wrote them, which is why one function produces both) and $incs them down, dropping whatever reaches zero. Deleting outright would tear holes in the graph of surviving conversations; leaving the weight would keep a residue of deleted content.
The subtle part: retry. _begin_turn() truncates the stored message array to the client's history length before appending, rather than blindly pushing. That's what makes retry correct — useChatTurn's handleRetry re-sends a shorter history, and truncate-then-append makes the stored array follow it instead of accumulating a duplicate copy of the turn being retried. A plain $push silently doubles history every time someone hits retry.
Titles are a third subagent. run_title_subagent() reuses the same _call_subagent() helper the Flowchart and Data Chart agents use — same forced-tool-call shape, same "return None and let the caller fall back" failure behavior, no new client or provider branching. A new conversation starts with a placeholder (the first message, truncated), and gets named on whichever comes first: its first diagram/chart, or its 6th message (3 questions and their 3 answers). Then titleLocked is set so the title never churns again. If no subagent client is configured the placeholder simply stays — a title is cosmetic and must never fail a turn.

How to follow the code

The whole app is four hops deep, tops. If you're new to this repo, read in this order — each step is the caller of the next.

01
src/App.tsx + src/hooks/

All client state, in four hooks that App.tsx wires together before picking a screen: useAuth (the signed-in user), useConversations (the saved list, which one is open, its title), useChatTurn (messages, streaming, retry, and the reducer that folds each SSE event into a message), and useComposer (the unsent draft and pending attachment, cleared together). Everything under src/components/ is a props-in view.

02
src/lib/api.ts

The only place that talks to the network from the frontend. streamChat() POSTs to /api/chat and hand-parses the SSE stream line by line, calling onEvent for each parsed JSON chunk; the auth and conversation calls all go through one small request() wrapper.

03
server/routes/chat.py

POST /api/chat, all async def: it loops over run_agent(...) and re-emits whatever it yields as an SSE event, persisting the turn around it — no LLM logic itself. Its siblings in server/routes/ hold the rest of the surface (meta.py, conversations.py, attachments.py), auth stays in server/auth.py, and server/main.py is app construction only — CORS, the body-size guard, the Mongo error handler, startup, and include_router().

04
server/agent.py

run_agent() trims the history to the last 3 messages, inlines any text/sheet attachment (attachments.py), looks up the picked model in models.py, forwards the memory Scope, hands off to exactly one of the three files in server/providers/, then intercepts any diagram/chart event on its way out — emitting trace events, then running it through subagents.py — before yielding it.

05
server/providers/{api,agent_sdk,openai_provider}.py

One file per backend transport, each independently readable. All three are async def ... yield ... generator functions producing the same AgentEvent dict shape, so routes/chat.py never branches on which one ran. Each also answers search_memory in its own tool loop — the one thing that can't be centralized in agent.py.

06
server/subagents.py

The Flowchart Agent / Data Chart Agent quality pass described above, called only from agent.py.

07
server/memory/

Indexing runs after the turn is over, off to the side of the hops above — but the read half is squarely on the path, twice over: select_context() before any provider runs, and search_memory from inside a provider's tool loop. Read __init__.py first: it names the five public functions (index_turn(), search(), select_context(), search_memory(), forget_conversation()) and maps the other twelve files.

Why it's easy to track

One state owner
App.tsx holds all mutable state; every other component is a pure props-in view. If a value on screen is wrong, that's where it comes from.
One shape crosses every boundary
The AgentEvent / ServerEvent dict (text | diagram | chart | trace | error | done, plus conversation | title from main.py's persistence layer) is produced by the provider (or by agent.py itself, for trace), forwarded verbatim by FastAPI, and consumed verbatim by App.tsx's reducer.
Almost no hidden state
No router, no global store. The database holds accounts and past conversations, but nothing about answering the current request reads from it — each /api/chat call replays the full message history it's given. The database is only ever written to, on the side.
Providers are drop-in
api.py, agent_sdk.py, openai_provider.py don't call each other or share helpers beyond the shared event shape.
One model catalog
server/models.py is the only place model IDs, providers, and availability rules live.
